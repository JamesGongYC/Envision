# v2.5 Day 1 — Foundation Migrations + Map Architecture Refactor

**Scope.** Two parallel tracks. Track A migrates the three simplest skills (housekeeping-retention, gdacs-ground-truth, forecast-evaluator) from Hermes to Modal — pattern validators before tackling ingestion and detection. Track B refactors the viewer map from single-layer to multi-layer architecture, including a layer panel UI, but doesn't ship any new visual content yet (existing forecasts still render identically). Each track is independent and can run in parallel Cursor sessions.

**Inherited:** `run(now, db)` signature; `ST_Force2D(...)` on geometry; reuse `envision-neon` Modal secret (already has `DATABASE_URL` and `ANTHROPIC_API_KEY`).

**New for Track A Day 1:**

1. **Migration shape per skill (mechanical, repeat 3×):**
   - Create `agent/modal_skills/<skill_id>/{SKILL.md, app.py, run.py}`.
   - Copy logic from existing `agent/skills/<...>/scripts/<...>.py` into `run.py` unchanged — same `run(now, db)` body.
   - `app.py` defines Modal Image, Secret reference, scheduled Function.
   - Test via `modal run`, deploy via `modal deploy`, retire matching Hermes cron registration.
2. **Image shape, by skill:**
   - `housekeeping-retention`: `modal.Image.debian_slim().pip_install("psycopg[binary]")`. Lightest — DB only.
   - `gdacs-ground-truth`: `modal.Image.debian_slim().pip_install("psycopg[binary]", "httpx", "feedparser")`. GDACS GeoRSS.
   - `forecast-evaluator`: `modal.Image.debian_slim().pip_install("psycopg[binary]", "shapely")`. DB + geometry ops for spatial matching.
3. **Schedule matches existing Hermes cron cadence:**
   - `housekeeping-retention`: `modal.Cron("0 6 * * *")` — daily at 06:00 UTC (was 24h on Hermes).
   - `gdacs-ground-truth`: `modal.Cron("0 */6 * * *")` — every 6h (was 6h on Hermes).
   - `forecast-evaluator`: `modal.Cron("0 7 * * *")` — daily at 07:00 UTC (was 24h; offset by 1h from retention to avoid contention).
4. **No reasoning generation in Track A Day 1.** Those three skills don't emit forecasts, so no `forecasts.reasoning` work. Detection skills (with reasoning generation) land Day 3.
5. **Retirement gate.** Each Hermes cron is removed ONLY after the Modal version has run successfully at least once via `modal run` AND inserted/processed rows visible in Neon. No "deploy and hope."

### Track A deliverables

#### A1 — Migrate `housekeeping-retention`

Net-new at `agent/modal_skills/housekeeping-retention/`:

- `SKILL.md` — describes purpose, retention windows (30d signals / 60d forecasts / indefinite for ground_truth, evaluations, skill_edit_proposals), schedule.
- `app.py`:
  ```python
  import modal
  image = modal.Image.debian_slim().pip_install("psycopg[binary]")
  app = modal.App("housekeeping-retention")
  
  @app.function(
      image=image,
      secrets=[modal.Secret.from_name("envision-neon")],
      schedule=modal.Cron("0 6 * * *"),
  )
  def scheduled_run():
      from run import run
      import os, psycopg
      from datetime import datetime, timezone
      with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
          return run(datetime.now(timezone.utc), conn)
  ```
- `run.py` — `def run(now, db) -> dict` returning counts deleted per table. Copy from existing Hermes script; no logic changes. Also executes `REFRESH MATERIALIZED VIEW CONCURRENTLY signal_catalog;` at the end.

Deploy:
```bash
modal run agent/modal_skills/housekeeping-retention/app.py::scheduled_run
modal deploy agent/modal_skills/housekeeping-retention/app.py
hermes cron remove <housekeeping_job_id>
```

**Acceptance:** Modal dashboard shows the scheduled function. `signal_catalog`'s `last_seen` updates on next refresh. Hermes cron list no longer contains housekeeping.

### Track B pre-decided

**Inherited from viewer conventions:** Next.js 14 App Router; Tailwind + shadcn defaults; Leaflet via dynamic import (`ssr:false`); ISR with 60s revalidation for server queries.

**New for Track B Day 1:**

1. **Layer state lives in a React Context.** Map and layer panel are both client components (Leaflet needs browser; toggle needs interactivity). Layer state shared via `LayerVisibilityContext` provider in `viewer/app/layout.tsx` (or higher in the tree above the map).
2. **localStorage persistence.** Layer-state context syncs to `localStorage["envision.layers"]` via `useEffect`. On first paint, server-rendered HTML uses defaults (forecasts on, rest off); after hydration, persisted state takes over. Brief flash of default state on first visit is acceptable.
3. **Layer panel UI stub for Day 1.** Build the component with a tree of checkboxes, but Day 1 only has one entry that actually controls a layer: `Forecasts`. Other entries can be placeholders (disabled checkboxes labeled "FIRMS hotspots (coming v2.5 Day 2)") to validate the tree structure renders correctly.
4. **No visible change to the existing user experience.** End state of Track B Day 1: viewer looks identical to current production. The architecture is refactored, but the only active layer is the existing Forecasts layer. Days 2–3 add the new visible layers.
5. **No backend changes.** All work is in `viewer/`. No new queries, no DB schema, no API routes.

#### B2 — `LayerVisibilityContext`

`viewer/components/layer-visibility-provider.tsx` — client component, `'use client'` directive.

```ts
const LayerVisibilityContext = createContext<{
  visibility: LayerVisibility
  toggle: (id: LayerId) => void
  setAll: (state: Partial<LayerVisibility>) => void
}>(...)

export function LayerVisibilityProvider({ children }: { children: ReactNode }) {
  const [visibility, setVisibility] = useState<LayerVisibility>(DEFAULT_VISIBILITY)
  
  // Load from localStorage on mount
  useEffect(() => {
    const stored = localStorage.getItem('envision.layers')
    if (stored) setVisibility(JSON.parse(stored))
  }, [])
  
  // Persist on change
  useEffect(() => {
    localStorage.setItem('envision.layers', JSON.stringify(visibility))
  }, [visibility])
  
  // ... toggle, setAll
}

export const useLayerVisibility = () => useContext(LayerVisibilityContext)
```

Mount the provider in `viewer/app/layout.tsx` wrapping the page content.

## Notes / gotchas

**Track A:**

- **Modal secret precondition.** `envision-neon` must exist from v2 Day 4. Verify with `modal secret list`. If absent, recreate before any `modal run`.
- **GDACS GeoRSS may have empty periods.** 0 new ground-truth events in 6h is normal off-disaster-season. Not a parser failure.
- **Forecast evaluator's class aliases must persist.** Per PROGRESS Day 4: `wildfire/WF/fire` and `typhoon/TC/cyclone` aliases. Don't lose these in the migration.
- **`hermes cron remove`** is the retirement command. Verify the job is actually gone with `hermes cron list` after each removal.
- **Don't archive Hermes skills yet.** Track A Day 1 only removes cron registrations. Full archive of `~/.hermes/skills/` happens Day 3 after all migrations land.

**Track B:**

- **Client component boundary.** The `LayerVisibilityProvider` must be in a client component file (top-level `'use client'`). It cannot be imported directly into a server component without a client boundary in between.
- **Hydration mismatch warning.** Server renders with `DEFAULT_VISIBILITY`; client may load different state from localStorage on first paint. Accept the brief flash; if it's jarring, use a `useEffect` flag to skip rendering until localStorage is loaded.
- **Don't refactor forecast-map's geometry-rendering internals.** Day 1 only changes WHO calls the rendering (via layer visibility check). The actual marker+popup code stays in `forecast-map-impl.tsx`.
- **Disabled checkboxes need to look disabled.** Operators must understand at a glance that some layers aren't available yet. Don't make them look identical to active ones.

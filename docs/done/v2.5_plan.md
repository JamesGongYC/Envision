# Envision v2.5 — Modal Consolidation + Ops UX Upgrade

A two-track phase between v2 and v3. Track A consolidates all production skills onto Modal (the option-B commitment from Day 4 of v2). Track B upgrades the map view from forecasts-only to a multi-layer visualization with interactive LLM-narrated forecast detail. Tracks are independent and parallelizable.

---

## 1. Premise

v2.5 does two things:

1. **Migrate the remaining 9 Hermes-resident skills to Modal.** v2 Day 4 put ECMWF, curator, and AIFS on Modal as the option-B template. v2.5 finishes the migration: 4 detection skills, 4 ingestion skills, 1 ground-truth poller, the evaluator, and the housekeeping-retention skill. Hermes is decommissioned at the end. v3 starts on a single unified platform.

2. **Upgrade the map view from single-layer forecasts to multi-layer signals + forecasts.** v2's substrate widening produced 11+ distinct signal types globally; the current viewer shows none of them. Track B exposes that substrate visually: toggleable layers per source/type, point markers for FIRMS-style data, polygons for grid-derived signals, all coexisting with the forecasts layer. Forecast markers gain a click-to-reveal dropdown showing LLM-generated narrative reasoning with a streaming-style typing animation.

Both tracks prepare for v3. Track A makes the runtime substrate uniform for the backtest harness and mutator. Track B makes the ops surface legible enough that human operators can review proposals against a visible system state.

## 2. Decisions log

| Decision | Choice | Rationale |
|---|---|---|
| Migration scope | All 9 remaining Hermes skills, full consolidation | Eliminate two-platform overhead before v3 |
| Migration shape | One Modal app per skill, reusing v2 Day 4 patterns | Patterns validated across 3 different skill types (ECMWF, curator, AIFS); replication is mostly mechanical |
| Detector generalization | Bundled with `wildfire-risk-elevated` migration | One PR per skill; avoids touching Hermes code that's about to be retired |
| Hermes decommissioning | End of Track A | All cron registrations removed; `~/.hermes/skills/` archived to `_archive/`; sync_skills.py retired |
| Reasoning generation | LLM-generated at detection time, stored in `forecasts.reasoning` | Reverses v1 decision (templated reasoning) for the UX value; cost ~$5/month at v2.5 volume |
| Streaming effect | Frontend animation on stored text, not live LLM calls | Predictable cost; avoids per-click LLM expense from viewer traffic |
| Map layer architecture | Single `/` route, toggleable layers, no separate `/signals` page | Single mental model; layer panel as the control surface |
| Point signal rendering | Leaflet.markercluster for clusters with >50 markers per zoom | FIRMS volume (10–50k hotspots active globally) breaks naive marker rendering |
| Polygon signal rendering | Native Leaflet GeoJSON; zoom-level visibility for fire_weather_grid + AIFS polygons | Polygons remain readable without aggregation; lower zoom hides cell-level detail |
| Forecast click UX | In-place dropdown popover, not page navigation | The `/forecast/[id]` deep-link route stays for permalinks; default interaction is inline |
| Authoritative kill-switch | Still deferred — `system_config` table | Per v2 Day 7 ticket; not load-bearing for v2.5 |

## 3. Explicit non-scope for v2.5

- The v3 evolution loop (Generator, Mutator, Backtest harness, Selector). That's v3 in full.
- Authoritative kill-switch UI via `system_config` table — defer until there's clear operational pain.
- Real-time alerting (push, email, SMS).
- Mobile-optimized viewer.
- New signal sources beyond what v2 shipped.
- Per-skill drill-in pages from cards (might surface in v3+).
- Live LLM streaming at click time (using stored reasoning instead).
- EFFIS/GWIS — still cut.

Total: 12 skills (matches `hermes cron list` count post-v2). All migrate. Plus reasoning-generation refactor on each detection skill (4).

Per-skill migration steps (≤2 hours each for ingestion, ~3–4 hours for detection):

1. Create `agent/modal_skills/<skill_id>/{SKILL.md, app.py, run.py}`.
2. Define Modal image: copy from ECMWF/curator template, adjust dependencies for this skill.
3. Configure schedule via `@modal.function(schedule=modal.Cron(...))` matching the previous Hermes cron cadence.
4. Test via `modal run`.
5. Deploy via `modal deploy`.
6. Verify in Modal dashboard.
7. Remove the Hermes-side cron registration: `hermes cron remove <id>`.
8. Confirm continued data flow in Neon (signals/forecasts/evaluations continue accumulating).
9. Mark skill migrated in PROGRESS tracking.

After all 12 skills migrated:
- Archive `~/.hermes/skills/` to `~/.hermes/skills.archive.<date>/`.
- Archive `agent/skills/` repo dir to `agent/_archive/skills/`.
- Retire `tools/sync_skills.py` (move to `tools/_archive/`).
- Update README to reflect Modal-only runtime.

## 7. Map view architecture (Track B detail)

Current viewer state (post-v2 Day 7): `/` renders a Leaflet map with forecast markers; clicking opens a popup with templated text; deep-link is `/forecast/[id]`.

Target state:

### Layer architecture

Three layer categories:

**Category 1: Point signals.** Markers per signal. Visual: small dots, color per signal_type, sized by recency.
- FIRMS hotspots (`source=firms_*, signal_type=hotspot`) — dense, requires clustering
- NWS fire alerts (`source=nws_alerts, signal_type=fire_warning`) — point centroid when polygon collapses at low zoom
- NHC cyclones (`source=nhc, signal_type=cyclone_advisory`) — sparse
- JTWC cyclones (`source=jtwc, signal_type=cyclone_advisory`) — sparse
- AIFS cyclone features (`source=aifs, signal_type=cyclone_feature`) — sparse, distinct color from observed advisories
- GDACS ground truth (`ground_truth` table, point geom) — historical events

**Category 2: Polygon signals.** Filled polygons with low opacity.
- NWS fire warnings (when polygon present, not collapsed)
- ECMWF fire weather grid (`source=ecmwf_open_data, signal_type=fire_weather_grid`)
- AIFS fire weather grid (`source=aifs, signal_type=fire_weather_grid`)
- AIFS high wind corridor (`source=aifs, signal_type=high_wind_corridor`)
- AIFS heavy precipitation band (`source=aifs, signal_type=heavy_precipitation_band`)
- Open-Meteo fire weather (point, but worth treating as buffered polygon at higher zoom)

**Category 3: Forecasts layer.** Markers per active forecast, colored by `disaster_class`, sized by `probability`. This is what `/` already shows; preserved as a layer.

### Layer panel

Right side of the map, collapsible. Tree structure:

```
☐ All sources
  ☐ Wildfires
    ☐ FIRMS hotspots
    ☐ NWS fire alerts
    ☐ Open-Meteo fire weather
    ☐ ECMWF fire weather grid
    ☐ AIFS fire weather grid
  ☐ Cyclones
    ☐ NHC advisories
    ☐ JTWC advisories
    ☐ AIFS cyclone features
  ☐ Weather features
    ☐ AIFS high wind
    ☐ AIFS heavy precipitation
  ☐ Ground truth (GDACS)
☑ Forecasts
```

Default: forecasts on, all signal layers off. Operator opts in. Persisted to localStorage.

### Performance: clustering and progressive load

- Point signals with >50 markers in viewport: use `leaflet.markercluster`.
- All signal queries server-side, returning GeoJSON FeatureCollections.
- Pagination: only fetch signals in current map bounds. On pan/zoom, refetch.
- For "show me everything globally": cap at 5000 points per layer, sample if exceeded, surface the cap to operator.

### Forecast click → dropdown popover

Click a forecast marker → opens dropdown anchored to the marker (not a separate page).

Contents:
- Skill name + version
- `disaster_class`, `probability` (with tooltip from v2 Day 7's `tooltips.ts`)
- `valid_from` / `valid_until` window
- **Reasoning narrative with typing animation:**
  - Stored `forecasts.reasoning` text rendered character-by-character with a blinking cursor
  - Animation speed: ~30 chars/second (configurable)
  - Skip-to-end button for impatient operators
- Link to `/forecast/[id]` for permalink/share

The typing animation is purely a frontend effect. No live LLM call. Data is the stored string from `forecasts.reasoning`, populated by detection skills (see §8).

### Components

New:

- `viewer/components/map-layer-panel.tsx` — checkbox tree, persists to localStorage
- `viewer/components/signal-layer.tsx` — renders one signal source as a Leaflet layer (point or polygon)
- `viewer/components/forecast-dropdown.tsx` — popover with typing-animation reasoning
- `viewer/components/typing-text.tsx` — generic typing-animation component, reusable
- `viewer/lib/signal-queries.ts` — GeoJSON query layer for signals by bbox + filters

Modified:

- `viewer/app/page.tsx` — adds layer panel, parameterizes map for multi-layer
- `viewer/components/forecast-map.tsx` — accepts active-layers prop, dispatches to signal/forecast layer components

## 8. Reasoning generation (Track B prerequisite)

Currently `forecasts.reasoning` carries templated strings per detection skill. v2.5 changes detection skills (during their migration in Track A) to call Sonnet with a structured prompt and store the result.

Prompt shape (one per detection skill):

```
You are explaining a probabilistic forecast emitted by an automated 
wildfire/typhoon monitoring system. The forecast is based on the 
following evidence: [structured summary of inputs and intermediate 
state from the skill's trace].

Write 2-3 sentences for a curious operator. Lead with what the system 
detected, then why it matters. Avoid jargon. Do not exceed 400 characters.

Be specific about the location and severity.
```

Cost: ~30–100 forecasts/day × ~500 tokens/forecast (input + output) × Sonnet pricing ≈ $3–8/month. Modest.

Sub-deliverable on each detection-skill migration: in addition to migrating to Modal, change reasoning emission to LLM-generated and store in `forecasts.reasoning`. This is why detection skill migrations are ~3–4 hours instead of 1–2.

## 10. Cut list

In order of expendability:

1. **AIFS polygon layers** (high wind corridor, heavy precipitation band). Keep cyclone features + fire weather grid; defer wind and precipitation layers to v2.6 if Track B runs long.
2. **Typing animation skip-to-end button.** Animation alone is enough.
3. **localStorage persistence of layer state.** Just default-off; operators retoggle each session.
4. **Reasoning generation as LLM call.** Keep templated reasoning, render with typing animation anyway. UX feel is similar; cost is zero.
5. **`wildfire-risk-elevated` generalization to ECMWF polygons.** Migration alone is sufficient; generalize in v3 prep instead.

**Never cut:**
- Migration of all 12 skills (incomplete migration leaves the two-platform problem).
- Forecast dropdown (the inline interaction is the central UX upgrade).
- At minimum, FIRMS + AIFS cyclone features + ECMWF fire weather grid as signal layers (the substrate-widening payoff).

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Migration breaks an active skill during transition | Per-skill smoke test before retiring Hermes cron; rollback by re-registering Hermes cron and reverting Modal app |
| FIRMS volume overloads Leaflet rendering | `leaflet.markercluster` at >50 markers per viewport; bbox-filtered queries; 5000-point cap with sampling |
| LLM-generated reasoning cost spikes if forecast volume grows | Cap at 100 forecasts/day generating reasoning; fall back to templated for excess; monitor weekly |
| Polygon rendering jank at low zoom (too many AIFS/ECMWF polygons globally) | Zoom-level visibility: hide grid polygons below zoom 4; show only at country/region zoom |
| JTWC geofencing not resolved by Modal migration | Add fallback User-Agent header; if still 403, mark as known issue and defer to v2.6 |
| Cursor IDE context window strain from large viewer refactor | Track B Day 1 ticket scoped to layer architecture only; subsequent days are additive |
| Detection skill migrations introduce regression in reasoning quality | Compare LLM-generated vs templated for 10 sample forecasts before each migration; tune prompt if needed |
| Modal free tier credit overrun | Currently <$2/month after migrations; reasoning generation adds ~$5; well under $30 credit |

## 12. Open questions

- Should `forecasts.reasoning` be regenerated if the LLM-generated version is unsatisfactory, or treated as immutable once written? (Lean: immutable, regen requires a new forecast.)
- Layer panel positioning — right-side collapsible vs. top horizontal bar? (Lean: right-side; map territory is more vertical.)
- Should signal-layer queries be cached on the server (Redis or similar) given Vercel cold starts? (Lean: defer until empirical evidence demands; ISR may suffice.)
- Display LLM reasoning generation date alongside text? (Lean: yes — operators want to know freshness; small footer line.)

## 13. v3 dependency contract — updates from v2.5

v3 backtest harness import path changes after migration:

- v3 plan §App A lists "the skill being mutated (passed per-ticket)" — after v2.5 the skill source lives at `agent/modal_skills/<skill_id>/run.py`, not `agent/skills/<category>/<skill_id>/scripts/`.
- v3's mutator + generator receive skill source code as text from `skill_lineage.source_code` per v3 plan §6; that path is unchanged.
- v3's shadow deployment can use Modal's native function-creation API to register shadow candidates dynamically — easier than dynamic Hermes cron registration would have been.

Anti-dependencies still hold (no typed DSL, no auto-promotion, evaluator is unmutable).
